time. Main, APK builds, signing and publication remain held. This is an
implementation/verification receipt, not native Android acceptance.

## Reproduced defects and fixes

### Exact paid transactions

The original Forge path accepted a `1e30` wallet, granted Arcane levels and
updated the purchase counter while both represented currency debits were
zero. Its queue path likewise granted ten levels without a represented debit.
The original Resonate path spent zero represented Sigils from the same wallet
while filling charge and consuming a run use. Both manual handlers also left
paid memory mutations behind when the primary write failed. Recovery-write
failure is a different endpoint: primary storage has already committed and
must remain authoritative.

Evidence: [Forge transactions](baseline/forge-transactions.json) and
[Resonate transactions](baseline/resonate-transactions.json). The earlier
[invalid Resonate setup](baseline/resonate-invalid-setup.json) is retained:
its missing Mythic rarity correctly prevented Resonate, and the corrected
reproducer explicitly establishes eligibility before asserting a purchase.

Both currencies and the purchased level increment must now represent the
exact quoted debit/delta. Manual Forge and Resonate stage a clone and roll it
back if primary storage has not committed. A committed primary endpoint
survives a failed recovery write. Queued purchases remain owned by the
existing live/offline transaction; tests fault actual offline processing and
verify rollback/retry instead of inventing per-level saves.

For capped bulk purchases, exact representability is not monotone in count.
The search therefore examines later funded counts even if an earlier total
cannot be represented. Uncapped fixed bulk remains all-or-nothing. Impossible
queued debits cannot create a zero-time economy boundary loop.

### Exact new price ledger

Applying the old floating geometric helper to the proposed new inputs
misrounded sixteen of 598 currency totals by one unit. Guardian Seal's first
Shards price became 14501 instead of 14500; Relay's first Lumen price became
493001 instead of 493000. The finite new ledger is the exact rational
geometric total rounded up once. Independent BigInt test arithmetic checks
every valid start/count/currency combination. Original eight price paths
remain unchanged. Zero count is the empty cost sum; every zero-count purchase
is rejected.

The [rational ledger comparison](baseline/prices-rational.json) retains all
inputs and mismatches. First prices are anchored to actual neutral nonboss
rewards at unlock minus one, multiplied by 1000 Lumen and 500 Shards. The
[six baseline pacing snapshots](baseline/pacing.json) are measured production
runs, not claims about time to unlock. In the mature fixture Auto-Ascend resets
Lumen during the window; gross production is not spendable cash.

### Conservative boss decisions and counter precision

The cached charge reference models real clipping, ordered casts, end-pass
Relay, boss refunds and Auto-Tap. It is a HUD estimate. Automatic Push/Farm
decisions use separate analytical bounds and a one-off burst budget.

An adversarial saved Support deadline showed that an exact-duration uptime
average was not a guaranteed lower bound. With Aurora at level50, Trim5 and
an epoch clock of `2000000000000`, the candidate promised 1519800 lower DPS.
Actual measured DPS was 1519799.993444882. At regeneration1519799.997, the
boss healed21.330758929 HP over6000 measured seconds rather than dying.
The fixed lower bound ignores Support buff uptime; the HUD and upper bound
still include it. The original failing seed and actual-HP replay are retained
under `debug/` and exercised by the calibration gate.

Retained lifetime tap counters can also exceed safe integer precision. A
counter of9007199254741000 stops incrementing and remains divisible by5, so
every actual tap receives Cadence. Other fixed ordinals receive none. A
one-in-five mean therefore cannot prove either controller bound. The lower
bound excludes Cadence; the upper allows its full bonus on every tap. If the
next60 taps cross safe integer precision, the HUD uses those actual sixty
increments as a one-minute reference. Saved counters are never rewritten.

The same class of error affected new same-run guards: an accepted
`ascendCount=1e30` remains numerically unchanged by `++`. A real Support boss
kill performed one Auto-Ascend, but old Spillway damage and Relay charge then
crossed the reset: the new enemy had10.5625/11 HP and Ember had10 charge.
The fix uses a transient object identity replaced by every actual Ascend.
All new same-run guards and the existing passive-interval guard use it, so
old-run time cannot credit new-run charge/automation. No persisted field is
added. [Before receipt](debug/unsafe-ascend-before.json) and
[reproducer](debug/unsafe-ascend-repro.cjs) establish the original failure.

## Regression harness corrections

Original frozen fixtures and their hashes remain unchanged. Where whole-state
historical comparisons encounter the sixteen additive fields, the test first
asserts every new level is zero and queue OFF, then projects only those proven
defaults out before the unchanged historical oracle. Original prices, factor
matrices, Deeds thresholds and the Luminous Tracking scroll tests remain.

Older Forge/R3 scenarios used `freeze()`, which sets the production reload
flag and disables real persistence. Correct transactional rollback exposed
that test-control assumption. These scenarios now pause ambient interval
callbacks while preserving production save eligibility. `feedbackTick`
restores its previous reload flag. New assertions prove that persistence is
enabled; the original purchase assertions still run. Historical very-large
funding fixtures now use an exact quoted budget, and separate assertions
require every unrepresentable huge-wallet purchase to be refused.

Other early failures were test assumptions: reload readiness must clear the
old bridge before waiting for the new page; an unlock-minus-one fixture must
not accidentally raise maxDepth through its current depth; offline summaries
must use their actual existing fields. These were corrected in test controls,
without changing game guards or weakening the historical results.

## Required acceptance and review boundary

Local source-bound receipts are under `candidate/`; the final PR body records
the exact commit, combined tree, workflow IDs, artifacts and integration SHA.
Local passes alone do not authorize integration. Full pre-merge validation,
Research Lab validation and the Forge workflow must all finish successfully
on the unchanged candidate and its combined development tree first.

The gates cover independent prices/effects, actual purchases and faulted
storage, all paid-value routes, real manual/live/offline/yielded Ascends,
twenty-row mobile input/large text/focus/scroll, actual V8 6.0 execution,
authoritative calibration, causal negative controls and the existing full
182-scenario regression suite plus its22 negative controls. Task/source and
tooling gates remain mandatory.

Code and evidence were reviewed by the primary agent and separate subagents.
That is not a human GitHub approval. Physical Android, native WebView60,
TalkBack and signed saved-app update acceptance remain open for the later
combined release. No APK is built or published by this feature.
